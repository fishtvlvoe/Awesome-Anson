# 覆盤交接框架

這份框架把一次合作的經驗，整理成下一次能重複使用的檢查點。它記錄「發生了什麼」與「下次怎麼做」，不代替報價、合約、客戶內部管理或事後追究。

## 1. 先分模式

| 模式 | 要回答的問題 | 可以產出 | 不要混入 |
| --- | --- | --- | --- |
| 覆盤清點 | 這次實際發生什麼、卡在哪裡、證據在哪裡 | 事實台帳、決策瓶頸、角色責任、下一案規則 | 未確認的執行計畫、報價、客戶人格評語 |
| 後續計畫執行 | 已確認的 Action 怎麼做、誰做、何時完成 | 任務、排程、追蹤結果 | 重新改寫覆盤結論、把推論變承諾 |

收到混合需求時，先宣告模式並只問一題確認。覆盤結束後，另以明確的 Action 清單進入執行模式；不可在同一段對話中靜默切換。

## 2. 事實與狀態

每一筆資訊都用下列格式保存：

`[狀態] 內容｜來源：檔名／訊息／交付物／Fish 明確確認｜時間：YYYY-MM-DD 或未知`

| 狀態 | 意義 | 可否當結論 |
| --- | --- | --- |
| `confirmed` | 檔案、紀錄、交付物或 Fish 明確確認支持 | 可以，但保留來源 |
| `recalled` | Fish 回憶或口述，尚未由原始資料交叉確認 | 不可以；需標明回憶 |
| `inferred` | Agent 從多筆資料推導出的解釋或假設 | 不可以；不能寫成客戶承諾 |
| `pending` | 找不到、互相矛盾或還沒決定的事項 | 不可以；列入未確認事項 |
| `action` | 下一步要做的事，不是過去發生的事 | 只能當行動；要有 owner／期限 |

`confirmed` 也要寫明是「來源確認」還是「Fish 確認」。若同一事項有多個版本，保留各版本與衝突，不自行選一個。

## 3. 盤點六個面向

用「人、事、時、地、物、交付物」逐項掃描。缺資料就寫 `pending`，不要以常識補齊。

| 面向 | 要記什麼 | 查證方向 |
| --- | --- | --- |
| 人 | 決策者、執行窗口、PM、實作者、審核者、被交接者 | 對話、信件、任務指派、文件署名 |
| 事 | 需求、承諾、變更、阻塞、已做與未做 | 逐字稿、issue、版本差異、會議紀錄 |
| 時 | 發生日期、回覆間隔、期限、延誤點 | 時間戳、日曆、commit、訊息紀錄 |
| 地 | 會議／溝通渠道、檔案所在位置、部署或驗收環境 | 連結、路徑、環境紀錄 |
| 物 | 素材、資料、工具、依賴、版本、權限 | 附件、repo、設定、交付清單 |
| 交付物 | 交付內容、版本、收件者、驗收狀態、缺件 | 檔案、URL、回覆、驗收紀錄 |

先建立時間線，再填角色與交付物。每個「誰應該做什麼」都要區分：當時明確指派、事後合理推論、或下一案建議。

## 4. 一題一題問與查證

1. Agent 先讀能取得的逐字稿、檔案、版本、任務與交付物。
2. 將未知事項排成優先序，只提出最影響覆盤結論的一題。
3. 問題要指出目前證據、缺口、建議答案與不確認的影響；不要把查檔案工作丟給 Fish。
4. Fish 回答後更新台帳，再選下一題。一次不問一串問題，也不在等答案時先改 HTML。
5. 找不到的事實保留 `pending`；「看起來」「應該」「大概」只可放在 `inferred`。

問法例：

> 我已在 `docs/meeting.md` 找到 A，訊息紀錄只支持 B；目前無法確認決策期限。這題先確認：本案是否有明確期限？若沒有，記為 `pending`，下一案規則只能要求事前設定期限。

## 5. F／N／G／A 雙層整理

四欄要同時放在同一張表，但語意不能互換：

| 代號 | 意義 | 寫法 | 禁止寫法 |
| --- | --- | --- | --- |
| F — Future | 下一案想複製的規則或希望達到的狀態 | 「接案前確認決策者與裁決者」 | 「客戶已同意下次這樣做」 |
| N — Now | 這次目前看得到的事實與狀態 | 「回覆時間未在文件中設定」 | 「客戶不負責任」 |
| G — Gap | N 與 F 的差距、證據缺口或衝突 | 「執行窗口與決策者未分開記錄」 | 用人格或動機填空 |
| A — Action | 具體下一步、owner、期限、驗證方式 | 「業務在下次報價前補角色表」 | 沒 owner／期限的願望 |

F 是可複製規則，不是客戶當時的同意；N 是觀察，不是評價。若 F 尚未經 Fish 採用，也標為 `inferred` 或 `pending`，不可假裝成組織政策。

## 6. 合作節奏檢查點

覆盤至少檢查以下五項，並各自標狀態：

| 檢查點 | 本案要找的證據 | 下一案可複製規則 |
| --- | --- | --- |
| 決策者 | 誰能核准範圍、取捨或變更 | 開始前寫出姓名／職稱與授權邊界 |
| 執行窗口 | 誰收資料、回覆細節、確認進度 | 決策者與日常窗口分開列出 |
| 回覆時間 | 實際回覆間隔與渠道 | 約定回覆窗口、逾時通知方式 |
| 決策期限 | 哪天前要定案，是否影響交付 | 每個關鍵決策附日期與逾期後果 |
| 認知分歧裁決者 | 需求、稿件或驗收爭議由誰拍板 | 事前指定單一裁決者與記錄位置 |

這五項是本案覆盤得到的檢查點。除非有原始證據，不得改寫成「客戶已同意」「客戶承諾」或其他歷史事實。

## 7. 中立與責任邊界

- 描述可觀察行為、時間、文件與影響；不用懶散、不專業、難搞等人格標籤。
- 「PM 沒有拿到資料／決策」是交付與協作觀察；不延伸成「客戶內部管理失敗」。
- 客戶內部的人力、授權、管理、預算與流程，除非有明確範圍及證據，否則標 `pending`，不列為 PM 應負責的補救工作。
- 可寫「本案缺少明確決策窗口」，不可寫「對方故意拖延」；後者若沒有證據只能是 `inferred`，通常不放入對外交接。

## 8. 給業務的結案交接

交接不是情緒摘要，而是下一個接案者能接手的最小完整包：

1. **始末**：案件背景、起點、重要轉折、目前收尾狀態。
2. **關鍵證據**：時間線、原始連結、交付版本、驗收或未驗收紀錄；每筆附狀態。
3. **決策瓶頸**：哪個決策未定、影響什麼、誰能裁決、期限是否存在。
4. **角色責任**：本案實際角色、明確指派、待確認角色；不補寫客戶內部責任。
5. **下一案規則**：用 F/N/G/A 逐項列出可複製檢查點、Action owner、期限與驗證。
6. **未確認事項**：集中列出 pending，包含「尚未確認誰同意」而不是默認同意。

## 9. 單頁 HTML 契約

HTML 是覆盤完成後的閱讀層，不是討論黑板。先一次整理完整內容與結構，再交給「網頁設計師」；設計者只處理可讀性、圖解與版面，不決定事實、狀態、責任或結論。

最低結構：

- 摘要：案件名稱、覆盤日期、模式、資料狀態與讀者得到什麼。
- 流程圖：起點 → 關鍵事件 → 決策瓶頸 → 交付／收尾；每節可回到相對連結證據。
- 角色責任：決策者、執行窗口、PM、交接業務與未確認角色。
- F/N/G/A：四欄表或四段卡片，清楚分開 Now 與 Future。
- 決策節奏：回覆時間、決策期限、分歧裁決者，標出缺資料。
- 下一步：Action、owner、期限、驗證方式；另列未確認事項。

單頁要能離線閱讀，引用使用相對連結，例如 `../docs/meeting-01.md` 或 `evidence/timeline.md`；不要放只有設計者看得懂的長段落，也不要在此 Skill 內部署。

## 10. 發布前完整性驗證

逐項核對並留下結果：

- 證據分級：每筆資訊有五種狀態之一、來源可追溯，推論與回憶未被寫成 confirmed。
- F/N/G/A：四類都有內容；N 是現況，F 是下一案規則；A 有 owner／期限／驗證。
- 角色責任：決策者、窗口、PM、業務與未確認角色沒有混寫。
- 決策期限：有明確日期就寫日期，沒有就明寫「未確認」，不能用模糊期限代替。
- 未確認事項：`pending` 集中可見，並說明不確認的影響。
- 連結與閱讀：相對連結可解析；手機窄版不需橫向捲動，流程圖、表格與文字仍可讀。

完成上述檢查只代表內容可發布；是否發布、放哪裡、何時部署，另等使用者指定。
