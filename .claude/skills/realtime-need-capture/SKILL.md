# Realtime Need Capture（即時需求拆解）

一句話定位：對談當下就把需求拆出來，不用等談完才回頭整理逐字稿。

## 觸發時機

- 業務員跟客戶對談進行中，人主動啟動這個 skill
- 對談結束、需求已初步拆解，準備交給 `demo-generation-deploy` 或報價流程時作為輸入來源

## 即時語音轉文字

- **已實作、可直接用的輸入來源**：`tools/realtime-voice/` 是本機收音＋辨識服務（FunASR SenseVoiceSmall，完全本機跑，簡轉繁後輸出）。業務員對談時啟動它，講話同時逐字稿會持續寫進 `tools/realtime-voice/output/<session-id>.md`。這個 skill 被觸發時，若使用者提供或指向這個路徑下的檔案，直接把它當作即時逐字稿讀取即可，不用再手動貼文字。
- 信心度低於門檻的片段，`tools/realtime-voice` 會標「[聽不清楚]」，意思是「聽不清楚，需要人工補」；不能靜默填入猜測文字，這個 skill 讀到時也要原樣保留這個標記，不能自己腦補內容
- 舊規劃（Cloudflare Workers AI Whisper／ElevenLabs Scribe v2 Realtime 雲端串流）尚未實作，目前以 `tools/realtime-voice` 的本機方案為準；若未來需要雲端方案再另外評估

## 即時回應（核心行為，每次讀逐字稿都要做，不是拆解完附註）

這個 skill 叫「即時」不是因為轉文字即時，是因為**回報要即時**。讀到逐字稿（不管是整段講完，還是對談中途被叫起來看目前進度），固定順序回四件事：

1. **客戶反應了什麼**：逐字稿裡客戶（不是業務員自己）明確表達的內容，逐條列出。客戶根本還沒開口回話時要直接講「客戶還沒回應，這段都是你自己在講」，不能腦補客戶說了什麼
2. **拆解成目前的樣子**：套人群/場景/痛點/需求/解決方案（或服務型 12 格），標好三態
3. **給業務員（Fish）的下一步建議**：不是甩一張「你少問了 A、B、C、D」的清單。想過拆解結果後，判斷當下最關鍵的缺口是哪一個，只給**一句**具體建議——「建議你接下來這樣問：___」或「建議先追問：___，因為 ___」。一次一個建議，不是把所有待確認欄位都列成問題清單丟出去
4. Fish 看了這句建議，自己決定要不要照講、要不要接著問下一句——**不是這個 skill 自動決定整個對談的問題順序**，它只給下一步的判斷，主導權在 Fish

第 3 點取代原本「待確認欄位 → 自動產出待問清單」那種一次列全部的做法：清單留給拆解表格本身（讓 Fish 事後查閱用），但**即時回應只給一個當下最該問的建議**，這樣才叫「輔助」不是「代替判斷」。

## 即時拆解

- 一般任務：拆成人群/場景/痛點/需求/解決方案五類，五個欄位每次都要填，真的問不出來就標「待確認」，不能留空
- 服務型任務：改用服務前/中/後 × 4 個檢查點的 4×4＝12 格拆解法
- 每個拆解項目標三態：「已確認/待確認/我猜的」（沿用案神既有 project-manager 的標記慣例），「我猜的」項目不能被系統自動升級成「已確認」

## 第六格（選填）：引薦/轉介機會

跟前五格不一樣，這格**不是每次都要填**——只在逐字稿裡真的出現對應訊號時才出現這個欄位，沒有訊號就不出現，不是「問不出來標待確認」。

對象不限 BNI 這類商務人脈場合，**更常見的是客戶或朋友順口提到的引薦**（例如「我朋友也在做類似的事」「我認識誰誰誰可能也需要這個」）。案神既有的五分類只問「這個人要不要簽約」，會漏掉這種話，這格是專門接住它的。

三態標記沿用既有慣例：客戶明確提到具體對象或場景 → 已確認；客戶模糊提到「可能有認識的人」→ 待確認；案神自己推測可能有引薦機會但客戶根本沒提 → 我猜的。**這格特別容易被腦補**，「我猜的」一樣不能自動升級成「已確認」。

## 待確認欄位 → 自動產出待問清單（不能只標「待確認」就停住）

- 任一欄位標「待確認」或「我猜的」，MUST 同步產出對應的一句「要問客戶的問題」，白話、可以直接照著問，不是欄位名稱的翻譯
- 輸出時待問清單跟拆解表格放在一起給業務員看，讓業務員知道下一輪對談要補問什麼，不是拆完就結束
- 若整份拆解「已確認」欄位不到一半，明講「這輪資料不足，建議先帶著待問清單回去問完，不要送進報價流程」

## 輸出格式

產出「即時需求拆解資料包」，欄位比照案神既有 PM-to-Quote Data Pack 擴充：

- 新增 `capture_mode`（`realtime` / `post-hoc`）
- 新增 `decomposition`（人群/場景/痛點/需求/解決方案 或 12 格陣列，每格附三態標記）
- 新增 `open_questions_for_next_round`（待確認/我猜的欄位對應的待問清單，比照 `contracts/PM-TO-QUOTE-DATA-PACK.md` 既有 `open_questions` 欄位慣例）

這份資料包會被 `commercial-proposal-quotation-specialist` 讀取，既有報價邏輯不受影響地繼續運作。比照 `contracts/PM-TO-QUOTE-DATA-PACK.md` 的交接停止點規則：`已確認` 不到一半時不得直接送進報價流程，先回頭問完待問清單。

## 不是什麼

不是常駐系統，不背景一直跑。只在人啟動對談的當下運作，對談結束這個 skill 的任務就結束，不留任何排程。
