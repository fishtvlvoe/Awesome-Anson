# Case Page（網頁對焦版本）

一句話定位：把已確認的提案/內容，做成一份能直接開的獨立網頁。

## 適用時機

- commercial-proposal-quotation-specialist 已交出「已確認提案內容」
- 客戶想先看網頁草稿，不需要正式簡報格式
- 小白拿 Awesome-Anson 公開 repo 連結丟給自己的 AI（Codex、Claude Code 這類），走到這一步需要生成頁面

跟簡報師是平行關係，不是誰取代誰：兩者吃同一份「已確認提案內容」，各自產出不同格式的輸出。

## 命名依據

案神的 Skill 一律用英文 kebab-case 命名（`ppt-master`、`kimi-slide`、`engagement-quote`），人格化的「XX 師」名字保留給 Agent（簡報師、開課師）。`case-page` 呼應「案神」的「案」字，不做成 Agent——它不需要自己判斷、不需要問使用者問題，純粹是一個生成動作。

## 前置：確認輸入內容

生成前先檢查提供的內容是否還帶有「待確認」「我猜的」這類未解標記。

- **有未解標記** → 不生成頁面，列出未解項目回報給呼叫方，請對方先確認完再回來
- **沒有未解標記** → 進入生成步驟

不得在內容不完整時硬生一份空殼頁面充數。

## 生成規則

- 輸出：單一自包含 `.html` 檔案
- CSS：全部寫在 `<style>` 內，不連外部 CSS 檔或框架 CDN
- 字體：宣告字體堆疊要有本機系統字體備援，內容本身不依賴需要付費或登入才能載入的字體服務
- 檔名：`<案件識別名稱>-case-page.html`（識別名稱取自提案的客戶/案件名稱；呼叫方也可以指定輸出路徑）
- 驗收：產出的檔案用瀏覽器以 `file://` 協議打開，關閉網路連線也要完整正常顯示，不破版

## 視覺呈現

- 不套單一固定樣板：依內容本身（產業、受眾、語氣）挑選對應的配色與字體，避免每次輸出都長一樣
- 色彩用 CSS token 定義，同時支援淺色／深色兩種模式（`prefers-color-scheme`），兩種模式下文字對背景都要有清楚的對比（WCAG AA：一般文字 4.5:1、大字/粗體 3:1）。小標籤、eyebrow 這類小字如果用強調色，務必用小字的門檻（4.5:1）驗證，不能只驗證大字通過就當作全部過關——實測過強調色在淺色底上用在小字會不夠深
- 標題與內文字體分開配對，不要整頁只用同一種字體撐到底

這條原則跟案神既有 Skill `kimi-slide`「依內容判斷、不套死規則」的精神一致。

## 明確不做的事

- 不部署上網（GitHub Pages、Cloudflare Pages 都不是這個 Skill 的工作）
- 不管理任何 GitHub/GitLab 帳號或 OAuth
- 不產生分享連結、不做存取控制（不設密碼、不設到期時間）

產出檔案之後要不要放上網、放哪裡，是呼叫方（Fish、簡報師、或小白的 AI）自己決定的事，不是這個 Skill 的職責。

## 不使用 note-bridge

這個 Skill 不呼叫、不整合 [note-bridge](https://github.com/chuangkevin/gitea-html-viewer) 或任何其他需要 GitHub/GitLab OAuth 登入才能寫入的 Git 協作平台。

理由：note-bridge 的「寫入」動作綁定帳號登入，這對案神服務的兩種對象都是不必要的門檻——案子的客戶通常沒有 GitHub 帳號；小白自己的 AI 也不該被要求先幫他辦一個帳號才能生成頁面。自包含 HTML 不需要登入、不需要帳號，誰都能開。
