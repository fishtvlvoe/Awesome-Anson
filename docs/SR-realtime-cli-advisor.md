# SR：案神即時 CLI 顧問工作流

狀態：Draft，交給 Claude Code（CC）開發
日期：2026-08-26
優先級：High
取代方向：現有「錄音頁面顯示分析、由 IDE Agent 手動監看」的工作方式

## 1. 這次要解決的真實問題

案神實際陪同客戶訪談時，現在的流程是：

```text
客戶對談
  ↓
錄音頁面轉成逐字稿
  ↓
Fish 切到 IDE
  ↓
手動請 CC 讀逐字稿
  ↓
CC 才分析客戶目前的需求
```

這個流程有四個直接問題：

1. 錄音工作台只完成「收音＋轉文字」，沒有主動顧問。
2. Fish 必須中斷客戶對話，切到 IDE 才知道下一步要問什麼。
3. 三欄面板增加閱讀負擔；對談時真正需要的是一句判斷與幾個可選回應，不是一直盯著分析面板。
4. 現有右側「AI 顧問」部分是前端寫死的示範回覆，不是真正連到 Agent。

因此目前產品比較像「錄音工具＋IDE 交接」，不是「立即顧問」。

## 2. 產品重新定位

案神的即時產品改成：

> 錄音介面負責把現場對話送成逐字稿；CLI 顧問自動監控逐字稿，套用案神的心智模型，在客戶每次回答後主動列出目前現況與 1／2／3 回應選項。

CC／IDE 只負責開發、除錯與會後深入整理，不再是客戶訪談中的必要操作介面。

## 3. 目標使用流程

業務只需要執行一個啟動指令：

```text
啟動案神即時顧問
  ↓
錄音服務與 CLI 顧問同時啟動
  ↓
客戶開始說話
  ↓
錄音介面轉成逐字稿
  ↓
客戶回答後停頓約 2～3 秒
  ↓
CLI 顧問自動讀取新增內容
  ↓
套用案神心智模型與目前案件狀態
  ↓
CLI 顯示現況與 1／2／3
  ↓
業務輸入數字
  ↓
CLI 顯示可以直接對客戶說的下一句
```

CLI 顯示格式示例：

```text
[案神] 客戶目前現況
已確認：第一階段最重要的是預約與提醒。
尚未確認：付款、會員功能是否要延後。
報價影響：核心範圍可以先收斂，進階功能可列第二階段。

[案神] 建議下一步，請選擇：
1. 確認第一階段成功標準
2. 追問哪些功能可以延後
3. 轉問預算與維護方式

請輸入 1／2／3，Enter 跳過，q 結束：
> 1

[案神] 建議你直接問：
「所以第一階段先完成預約與提醒，這兩項就是最重要的成功標準，對嗎？」
```

`1／2／3` 是業務選擇建議，不是案神代替業務對客戶發言。業務仍然保有最後判斷權。

## 4. 元件責任

### 4.1 錄音介面

只保留必要功能：

- 開始／停止收音。
- 麥克風權限與收音狀態。
- 即時轉成繁體中文逐字稿。
- 將逐字稿寫入本次案件的 session 檔案。
- 顯示最基本的「顧問已連線／顧問未連線」狀態。

錄音介面不再承擔：

- 三欄分析面板。
- 右側顧問對話框。
- 前端寫死的 AI 回應。
- 要求 Fish 點擊選項才能啟動分析。

逐字稿仍可保留為除錯與會後查閱用途，但不是對談中的主要操作畫面。

### 4.2 CLI 顧問

CLI 顧問是本次 SR 的核心：

- 由啟動流程自動啟動，不要求 Fish 另開 IDE 或手動執行 monitor。
- 只在本次錄音 session 存活期間運作。
- 監控逐字稿新增內容與 session state。
- 在自然停頓後自動分析，不等 Fish 下「請分析」指令。
- 顯示客戶目前狀況、尚未確認事項、報價影響與 1／2／3。
- 接收業務輸入的數字，產生可直接說出口的回應。
- 將選擇、採納狀態與判斷依據寫入 session event。
- session 結束時正常停止，不註冊 daemon、launchd 或永久背景服務。

### 4.3 案神心智模型與 Agent 路由

每次分析都先使用 `realtime-need-capture` 的即時需求拆解規則，再依對話訊號路由到適合的案神能力：

- 一般需求：人群／場景／痛點／需求／解決方案。
- 服務型案件：服務前／中／後的 4×4＝12 格拆解。
- 需求、範圍、成功標準：PM／需求分析能力。
- 價格、付款、保固、維護、交付：報價師能力。
- 網站、Dashboard、Demo：網頁設計師能力。

路由只產生「目前應該怎麼問」的建議，不直接改報價、不直接改程式、不直接部署 Demo。要進入開發、報價或部署流程，必須由 Fish 明確選擇並確認。

## 5. 自動分析觸發規則

### 5.1 觸發時機

顧問必須自動觸發：

- 新增逐字稿後，超過約 2～3 秒沒有新內容。
- 連續對談沒有自然停頓時，累積約 30～60 秒強制分析一次。
- 每次觸發要把連續的短片段合併成一個可理解的對話回合。

不能以目前瀏覽器的 700ms 音訊切段直接當成一次顧問回合，否則會過度頻繁呼叫模型。

### 5.2 只在適當時機列選項

- 客戶剛回答完：顯示現況與 1～3 個下一步回應選項。
- 業務員正在連續說明：先更新背景，不急著列出一串問題。
- 只有業務員自己講、客戶尚未回應：顯示「客戶尚未回應」，不可假裝已取得客戶需求。
- 內容太短、聽不清楚或角色不明：保留待確認狀態，不把猜測寫成客戶承諾。
- 上一次分析尚未完成：不要重複呼叫；完成後再處理排隊中的新內容。

### 5.3 每次分析輸出

CLI 顧問至少要輸出：

```json
{
  "client_response": ["客戶明確說出的反應"],
  "current_state": "客戶目前狀況的一句話",
  "confirmed": ["已確認事項"],
  "open_questions": ["尚未確認但會影響下一步的事項"],
  "quote_impact": "對範圍、預算或維護的影響",
  "mental_model": "本次使用的案神心智模型",
  "evidence": ["支持判斷的逐字稿內容"],
  "recommended_next_move": "目前最重要的一個下一步",
  "response_options": [
    "可以直接對客戶說的選項一",
    "可以直接對客戶說的選項二",
    "可以直接對客戶說的選項三"
  ],
  "speaker_attribution": [
    {
      "segment_id": "seg-0001",
      "role": "pm|client|unknown",
      "confidence": 0.0,
      "reason": "文字或對話脈絡依據"
    }
  ],
  "route": "realtime-need-capture|pm|quote|web-design|none"
}
```

`response_options` 最多三個。`recommended_next_move` 只有一個，不要把整份待確認清單一次丟給業務。

## 6. PM／客戶角色判斷

### 6.1 結論

第一版不需要聲音辨識模式才能運作。

從文字與對話脈絡可以「大致推定」誰是 PM、誰是客戶，但不能宣稱 100% 識別。PM 身份應在 session 開始時由啟動者直接指定；客戶角色則由文字內容、問答順序與對話狀態推定。

### 6.2 第一版角色規則

1. Session 啟動者預設為 PM／業務員，這個角色不是由模型猜。
2. PM 的提問、重述、方案說明與確認句，通常標為 `pm_candidate`。
3. 回答自身需求、描述現況、提出限制、表達預算或同意／拒絕的內容，通常標為 `client_candidate`。
4. 模型只回傳 `pm`、`client` 或 `unknown`，並附信心度與判斷依據。
5. 信心不足時標 `unknown` 或 `pending`，不得自動改寫成「客戶已確認」。
6. 即使角色不確定，也可以先抽取「對話中明確出現的需求」，但要把來源標成待確認。

### 6.3 為什麼不把聲音辨識列為必要功能

聲音辨識解決的是「這個聲音像不像事先註冊的某個人」，不是「這句話在對話裡扮演什麼角色」。

- 單一 PM＋單一客戶：文字與問答脈絡足以支援第一版顧問，聲音辨識不是阻塞條件。
- 多位客戶或多人同時插話：單靠文字不能穩定知道每句話是哪一個人說的，這時才需要 speaker diarization 或人工指定。
- 聲音辨識／聲紋比對：列為後續增強，不得讓第一版因 profile 未建立而無法使用。

必要時 CLI 提供低成本人工修正：

```text
這段角色不確定：
1. 客戶
2. PM
3. 暫不判定
```

這是例外處理，不是每一段都要求業務標記。

## 7. Session 狀態與資料格式

目前只把新增逐字稿交給 Agent，會導致顧問忘記前面已確認的內容。新版必須保存可累積的 session state：

```json
{
  "session_id": "20260826-143000",
  "operator_role": "pm",
  "case_ref": "case-optional",
  "confirmed_facts": [],
  "open_questions": [],
  "current_mental_model": "",
  "quote_signals": [],
  "last_analysis_ts": "",
  "pending_response_options": [],
  "adoption_events": []
}
```

每次分析要把：

- 目前累積狀態。
- 上次分析後新增的逐字稿。
- 上次業務選擇的 1／2／3。
- 已確認與待確認事項。

一起交給顧問。不能只看最新 30 秒就重新猜整個案件。

真實客戶逐字稿、session state、事件與產出物要寫到使用者指定的案件 `caseRoot`，不可把真實內容當成 repo 原始碼提交。音檔仍維持本機保存。

注意：音檔不上傳不代表逐字稿不上雲。若 CLI 使用外部模型服務，啟動時要清楚顯示「逐字稿文字會送到哪個模型服務」。如果案件要求文字也不能離開本機，必須另做本機模型方案，不能模糊宣稱完全本機。

## 8. 啟動與停止契約

### 8.1 啟動

一個啟動指令要完成：

1. 啟動本機錄音／轉文字服務。
2. 建立並公布本次 `session_id` 與逐字稿路徑。
3. 自動啟動同一 session 的 CLI 顧問。
4. CLI 顯示顧問 ready、分析模型／Agent runner、資料保存位置與隱私狀態。
5. 任一元件啟動失敗時明確報錯，不可讓畫面看似正常但顧問根本沒有運作。

### 8.2 停止

- `q` 或停止收音後，CLI 顧問停止監控。
- 錄音 server 與 CLI 顧問一起結束。
- 不留下 monitor、Agent worker、daemon 或 launchd 服務。
- session state、逐字稿與事件保留在案件資料夾，供會後分析。

## 9. CC 實作範圍

CC 應先查現有實作並沿用，不另開第二套錄音服務。預期影響範圍：

- `scripts/start-realtime-voice.sh`：同時管理錄音 server 與 CLI 顧問的生命週期。
- `tools/realtime-voice/monitor_transcript.py`：改成具備 session state、自動觸發與 CLI 選項輸入，或拆成清楚命名的 `advisor_cli.py`。
- `tools/realtime-voice/server.py`：提供 session manifest、逐字稿／事件路徑與必要的狀態端點；不要把 Agent 呼叫塞進瀏覽器。
- `tools/realtime-voice/static/index.html`：收斂為錄音／轉文字介面，移除假 AI 回覆與不必要的三欄顧問操作。
- `tools/realtime-voice/README.md`：更新成一個指令啟動的使用方式。
- `tests/`：新增自動觸發、session state、CLI 1／2／3、角色推定與失敗狀態測試。

CC 不應：

- 先做更多面板再處理顧問閉環。
- 把 `claude`／`codex` 手動貼指令當成產品流程。
- 用前端條件判斷寫死 AI 回覆。
- 因為沒有聲音 profile 就阻擋單一 PM＋單一客戶的第一版使用。
- 讓顧問自動改報價、改程式或部署 Demo。

## 10. 驗收標準

### 必須通過

- 執行一個啟動指令後，錄音服務與 CLI 顧問都 ready，不需要另開 IDE 或手動啟動 monitor。
- 匿名 fixture 模擬 PM／客戶交替發言；客戶回答後自動觸發一次分析。
- CLI 顯示目前現況、已確認、待確認、報價影響與最多三個選項。
- 業務輸入 `1`、`2` 或 `3` 後，CLI 顯示對應的可直接回覆句，並寫入 adoption event。
- 每次分析都有 `mental_model`、`evidence`、`recommended_next_move` 與 `response_options`。
- 前一次已確認內容會留在 session state，下一次分析不得遺失。
- 客戶尚未回應時，輸出「客戶尚未回應」，不得腦補客戶需求。
- 文字角色判斷信心不足時標 `unknown`／`pending`，不得假裝聲音辨識完成。
- 沒有聲音 profile 時，單一 PM＋單一客戶流程仍可使用。
- 服務停止後沒有殘留 monitor 或背景程序。
- 真實逐字稿與 session state 不進 Git；測試 fixture 不含真實客戶內容、音檔或 secrets。

### 不列為第一版阻塞條件

- 多位客戶的自動聲音身份辨識。
- 完整 Dashboard 或三欄顧問面板。
- 顧問自動產生並部署 Demo。
- 顧問自動修改正式報價單。
- 顧問代替業務直接對客戶發言。

## 11. 建議開發順序

1. 先寫匿名 fixture 與 session state／analysis schema 測試。
2. 把現有 monitor 改成不需 IDE 手動介入的 CLI 顧問流程。
3. 把啟動腳本改成 server＋advisor 一起啟動與停止。
4. 加入文字角色推定與 `unknown` fallback，聲音辨識不列入阻塞條件。
5. 用真實 browser smoke 驗證「收音 → 逐字稿 → 自動分析 → CLI 1／2／3 → event 保存」。

完成定義不是 build 通過，而是業務可以在不切到 IDE、不看分析面板的情況下，靠錄音與 CLI 選項完成一輪客戶需求對焦。
