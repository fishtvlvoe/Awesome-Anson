## Context

`realtime-need-capture` 目前是一個「人主動啟動」的 Claude Code skill：業務員在對談時自己觸發，把逐字稿內容交給它拆解需求。它本身不是背景常駐服務，也沒有自動監看檔案的機制，逐字稿目前只能靠人工貼上對話框。

這個 change 要補的是「聲音變文字」這一段，讓逐字稿不用手動打字或貼上，但整體仍要維持「人啟動才動」的原則，不能變成背景常駐服務。

已經用真實模型跑過的驗證數據：FunASR 的 `iic/SenseVoiceSmall` 模型，本機下載後大小 936MB，用範例中文音檔測試 rtf（real-time factor）0.163，代表辨識速度遠快於講話速度，足夠支撐「邊講邊出字」；辨識輸出預設為簡體字，已驗證 OpenCC `s2twp` 設定檔可以正確轉成繁體（「开放时间早上9点」→「開放時間早上9點」）。

## Goals / Non-Goals

**Goals:**

- 業務員按鍵就能開始收音，講話同時畫面即時顯示辨識文字（繁體）
- 收音來源支援電腦瀏覽器與手機瀏覽器（同一 Wi-Fi 下用手機開網頁當麥克風）
- 辨識結果持續寫進一個固定路徑的輸出檔案，讓 Claude Code session 裡的人可以直接把這個檔案交給 `realtime-need-capture` 讀取，不用手動打字
- 全部在本機／區域網路運作，不上雲端、不產生 API 費用

**Non-Goals:**

- 不做背景常駐或開機自動啟動——服務只在業務員手動執行啟動指令的當下運作，對談結束手動關閉即結束
- 不做 `realtime-need-capture` 拆解邏輯本身的修改，只補上游輸入
- 不做多人語者分離，不做多場對談併發錄音
- 不做雲端部署，不牽涉 `case-page`「不部署上網」原則要處理的情境（這個服務本身就不上網）

## Decisions

### 收音介面：本機小網頁，不做獨立 App

用瀏覽器內建的 `MediaRecorder`／`getUserMedia` 做收音介面，而不是寫一個桌面或手機 App。理由：瀏覽器免安裝、電腦跟手機都能用同一份介面連線，開發與維護成本最低。取捨：需要瀏覽器允許麥克風權限，第一次使用要手動同意。

### 辨識引擎：本機 FunASR SenseVoiceSmall，不用瀏覽器內建語音辨識、不用雲端 API

三個方案已實測比較：
- 瀏覽器內建語音辨識（Web Speech API）：免安裝，但辨識品質差，之前被否決。
- 雲端 Whisper 串流（Cloudflare Workers AI）：中文辨識穩定，但要另外開發串流上傳機制，且每次轉錄都有 API 費用。
- 本機 FunASR SenseVoiceSmall（採用）：實測 936MB、rtf 0.163、辨識正確，完全免費、不用網路，缺點是需要先下載模型與 Python 相依套件（PyTorch 等），初次設置較重。

選本機 FunASR 的原因：既有免費又不用網路依賴，速度也驗證足夠支援即時場景，缺點（初次安裝重）只影響設置一次，不影響日常使用。

### 簡繁轉換：OpenCC `s2twp`，在伺服器端轉換後才寫入輸出檔

SenseVoiceSmall 原生輸出簡體字。選在伺服器端（Python 服務內）用 `opencc-python-reimplemented` 的 `s2twp`（簡體轉繁體，含台灣用語轉換）做轉換，而不是留給前端或人工事後轉換，理由是輸出檔案要直接可讀，不能讓使用者每次都要多一道手動轉換的步驟。

### 案神銜接方式：寫固定路徑輸出檔，人在 Claude Code session 裡手動指給 realtime-need-capture 讀，不做檔案監看常駐服務

`realtime-need-capture` 現在的設計是人主動觸發的 skill，不是背景監看服務。要維持這個「人啟動才動」的原則，這個 change 不新增一個常駐的檔案監看程式（那會變成背景常駐系統，違反案神現有原則）。改為：語音服務把逐字稿持續寫進固定路徑（`tools/realtime-voice/output/<session-id>.md`），業務員在 Claude Code session 裡呼叫 `realtime-need-capture` 時，直接把這個檔案路徑交給它讀取即可，跟現在「人工貼文字」的操作方式一樣輕，只是來源從「自己打字」變成「唸給電腦，電腦自動存成檔案」。

## Implementation Contract

**行為（Behavior）**：
- 業務員在終端機執行啟動指令後，本機服務監聽固定的 port（預設 `8420`），畫面顯示一個「開始/停止收音」按鍵
- 按下開始後，麥克風收音持續送進服務端；服務端每偵測到一段語音停頓（VAD 靜音判斷），就跑一次 SenseVoiceSmall 辨識，轉繁體後：(a) 透過 WebSocket 推回瀏覽器畫面即時顯示、(b) 附加寫入輸出檔案
- 按下停止後，服務停止收音與辨識，輸出檔案维持在磁碟上，服務進程仍在（可再按開始收音，不會結束整個進程），業務員自己在終端機按 `Ctrl+C` 才真正關閉服務——維持「人啟動才動」，不自動背景重啟

**介面 / 資料格式**：
- HTTP `GET /`：回傳收音介面頁面（`static/index.html`）
- WebSocket `/stream`：瀏覽器端把麥克風音訊塊（webm/opus）持續送到這個端點；伺服器端每完成一段辨識，回傳 JSON `{"text": "<繁體文字>", "ts": "<ISO時間>"}`
- 輸出檔案：`tools/realtime-voice/output/<session-id>.md`，每偵測到一段就附加一行，格式 `- [<ISO時間>] <繁體文字>`；`session-id` 由伺服器啟動時的時間戳產生
- 手機連線：伺服器啟動時印出區域網路 IP（例如 `http://192.168.x.x:8420`），業務員用手機瀏覽器開這個網址即可，跟電腦連的是同一個服務、同一個輸出檔案

**失敗模式**：
- 辨識信心過低或音訊太短/太吵：該段文字前標記 `[聽不清楚]`，不能靜默丟棄，也不能自動猜測填入
- FunASR 模型載入失敗（例如模型檔案損毀）：服務啟動時直接印出錯誤原因並結束進程，不能靜默啟動一個沒有辨識功能的服務
- 麥克風權限被拒絕：瀏覽器畫面顯示明確提示「需要允許麥克風權限才能開始收音」，不能只顯示空白畫面

**驗收標準**：
- `tests/test-realtime-voice-s2tw-conversion.js`：餵入已知的簡體字辨識結果，驗證輸出是對應的繁體字
- `tests/test-realtime-voice-writes-to-inbox.js`：模擬一段辨識結果，驗證輸出檔案裡出現對應格式的新增行
- 手動驗證：在同一台 Mac 上用瀏覽器實際講一句話，確認畫面即時顯示文字、輸出檔案裡出現對應內容

**範圍邊界**：
- 範圍內：本機收音介面、FunASR 辨識、簡轉繁、寫入輸出檔案、手機瀏覽器連線
- 範圍外：`realtime-need-capture` 內部拆解邏輯的任何修改（只在 SKILL.md 補充說明輸入來源可以是這個輸出檔案）、雲端部署、多人語者分離、自動監看檔案並自動觸發拆解（觸發仍由人執行）

## Risks / Trade-offs

- [風險] 第一次設置要下載 936MB 模型與安裝 PyTorch，設置時間長 → 對策：`README.md` 寫清楚一次性安裝步驟與預期耗時，設置只需要做一次
- [風險] Mac 效能不足時，辨識可能跟不上講話速度 → 對策：已用實測 rtf 0.163 證明速度足夠，若日後 Mac 效能明顯不足，才需要重新評估
- [風險] 手機跟電腦要在同一個 Wi-Fi 才能連線，若業務員在客戶現場用手機熱點，電腦連不上手機的網路就無法用手機當麥克風 → 對策：一開始就用電腦本身的麥克風收音當主要路徑，手機收音是加分選項，不是唯一路徑
- [風險] 服務停止收音後進程仍在背景等待下一次啟動，如果業務員忘記關閉，會變相變成常駐 → 對策：README 明確要求對談結束後按 `Ctrl+C` 關閉，且服務本身不做開機自動啟動、不寫入任何排程設定
